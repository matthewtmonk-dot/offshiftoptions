## Project Identity & Purpose

- **Product:** Off Shift Options (formerly "LST Buddy") — a private, two-user PWA for Matt and Eric to run a disciplined, low-stress cash-secured-put options workflow: scan candidates, research tickers, track trades, share recommendations, chat, and measure performance over time.
- **Users:** Private two-user application only. No public signup exists or is planned.
- **Not:** a brokerage, a public trading platform, a financial advisory service, or an automated trading bot.
- `PRODUCT_VISION.md` (repo root) is the long-term north-star document; this file is the operational current-state snapshot.

## Product Model: Scan / Research / Track / Performance

Four connected jobs — a change that blurs the boundary between two of them needs a second look before merging:

1. **SCAN** — purely technical PASS/FAIL/UNKNOWN + setup score. Never influenced by personal opinion.
2. **RESEARCH** — the user's personal judgment of a ticker (Like/Watch/Neutral/Avoid/Never Trade). Purely personal: **never changes what Scan computes.** A `NEVER_TRADE` item is hidden from Scanner's default view but its score/status/label are computed exactly as if it weren't excluded.
3. **TRACK** — the append-only historical record of what actually happened (`Campaign`/`CampaignEvent`): every roll, assignment, covered call, and outcome, preserved forever.
4. **PERFORMANCE** — whether the strategy is working over time, built from confirmed ledger/broker facts, never a raw balance-delta guess.

Research *feeds* Scanner (widens the live-scan universe, personal exclusion hides a candidate from the actionable list) but never *replaces* it. See `docs/DATA_MODEL.md`, `docs/LST_DOMAIN.md`, `docs/SCANNER_RULES.md` for subsystem depth.

## User / Data Ownership & Privacy Invariants

- **Matt and Eric are fully separate account owners.** One user's balances, positions, transactions, imported records, campaigns, settings, performance, projections, or research opinions must never populate, affect, or be blended into the other's — proven throughout by DB-integration tests (privacy, workflows, account ledger, research). Sharing a record (`SHARED` visibility) makes it *visible* to the other user; it never merges it into their own totals/balances/P/L.
- `PRIVATE` data stays private to its owner; `SHARED` is visible to both, per `src/lib/privacy.ts` (`assertCanReadRecord`/`assertCanMutateRecord`). Authorization is enforced **server-side only** — UI hiding is never relied on for security.
- Research opinions (Like/Watch/Avoid/Never Trade, notes, manual fields) default to **PRIVATE** and post no shared activity — even the bare fact that a user researched a ticker is personal unless explicitly shared.
- Tracker Performance is always computed from the viewer's **own** accounts/campaigns only, never the scope-filtered Mine/Buddy/Both list — switching scope can make a buddy's shared campaigns *visible*, never blended into your own figures.

## Read-Only Brokerage Constraints

- **This application does not place trades.** No buy/sell/place/submit/replace/cancel-order or algorithmic execution exists or may be added without Matt explicitly changing this requirement. Schwab's Order Limit is configured at **0**.
- Allowed Schwab methods are read-only: `getQuote`, `getPriceHistory`, `getOptionChain`, `getInstrument`, `getMarketHours`, `getAccounts`, `getPositions`, `getTransactions`, `getOrders` (historical observation only).
- Brokerage account data is **user-scoped**: a user's own OAuth connection, tokens, balances, positions, and transactions are never used to serve another user's requests. Personal-broker provider resolution has no cross-user fallback path at all.
- Shared market-data fallback (one user's connection serving another's read-only quote request) remains **disabled** (`DISABLED_POLICY_NOT_VERIFIED`) — no official Schwab documentation has confirmed this is permitted. Do not enable it without that verification.
- **Bounded provider usage:** live scans use a fixed starter ticker universe (currently 13 symbols + the user's own Research union), cap option-chain calls, and use bounded concurrency (`SCAN_FETCH_CONCURRENCY`) — not unbounded polling. Alpha Vantage's 25-requests/day budget is shared across both users and the Scanner and is protected by an explicit queue/priority design (`docs/ARCHITECTURE.md`, Alpha Vantage detail in the archive).
- **A linked broker position record must never supply a current-position mark merely because it belongs to the campaign** (`src/domain/finance/currentPositionMark.ts`, `resolveCurrentCostToClose`) — every candidate is validated against `getCurrentOpenPut`'s own account/underlying/strike/expiration/quantity before being accepted, so a rolled campaign's pre-roll contract (which stays linked forever) can never value the post-roll leg. Freshness policy (`classifyMarkFreshness`, `marketCalendar.ts`): CURRENT_SESSION/LAST_SESSION are usable, STALE/MISSING are rejected outright — calendar-day-only, never invented intraday precision. A rejected/unavailable mark means an honest PENDING/INCOMPLETE `currentPLStatus` (Ticket 4), never a stale number or a fabricated zero.
- Tokens/secrets/developer credentials are encrypted at rest (AES-256-GCM) and never reach client-side JS, logs, or this documentation.

## Campaign / Event-History Invariants

- `CampaignEvent` rows are **append-only** — no workflow ever updates or deletes an existing event. A roll writes a `ROLL_PUT_CLOSE` + `ROLL_PUT_OPEN` pair sharing a `groupKey`; the old and new legs both remain in history, never overwritten. The full lifecycle (open → roll → assign → covered call → close) is always reconstructible from events alone.
- **`getCurrentOpenPut` (`src/domain/finance/campaigns.ts`) is the single authoritative definition of "what put is open right now"** — used identically by the Dashboard, Tracker, and Performance (`summarizeCampaignProgress`). Do not add a second, competing interpretation of current-leg state anywhere; delegate to this function instead. Its event ordering (`compareEvents`) is fully deterministic (`occurredAt` → `sortOrder` → `createdAt` → `id`), so the same event history produces the same result regardless of array/query order — this was a real, fixed bug (see Roadmap status below).
- **Conservative expiration confirmation:** a short put is only marked expired-worthless when broker evidence is complete (positions COMPLETE, all transaction categories COMPLETE, persistence COMPLETE, the transaction window covers expiration, no remaining matching option, no acquired long position) — any failed/partial/incomplete evidence keeps the campaign OPEN (`EXPIRATION_EVIDENCE_INCOMPLETE`) rather than guessing. Never invents an OTM quote or a zero-cost close.
- A `CampaignStatus` of `OPEN`/`ASSIGNED`/`CLOSED` and a `Campaign.visibility` of `INHERIT`/`PRIVATE`/`SHARED` (inheriting from the parent `TradingAccount` when `INHERIT`) fully describe lifecycle/visibility state — see `docs/DATA_MODEL.md`.

## Reconciliation / Import Safeguards

- Never use a filename or CSV row number as economic identity. Use `BrokerRecord.fingerprint` (the exact economic fact — backs DB-level dedupe) and a separate `identityKey` (the same real-world slot — account+date+symbol+action — without the financial fields, used for conflict detection).
- A same-`identityKey`-different-`fingerprint` match is always a `CONFLICT`, stored as a separate row for manual review — **never a silent overwrite** of the original.
- Import classification is `NEW | DUPLICATE | CONFLICT | NEEDS_REVIEW | INVALID` — never guessed. Preview-before-persist: uploading/previewing a file never mutates financial history by itself; only an explicit Confirm persists `BrokerRecord`s.
- `CampaignEvent`s remain the sole trading-performance source of truth even for a campaign created from reconciled broker evidence — a Realized Gain/Loss import may only *verify* a campaign's result, never add to it.
- A historical link alone cannot exclude live broker exposure: account, current contract, quantity, and unique campaign coverage must agree. The same contract in two accounts has two distinct link keys. Unknown/ambiguous exposure remains visible rather than being silently removed.

## Scanner — Purpose & Current Constraints

- `src/domain/scanner` evaluates each criterion PASS/FAIL/UNKNOWN; overall result is FAIL if any criterion fails, else UNKNOWN if any is unknown, else PASS. **Gating** rules (price, volume, OI, bid, spread, delta, earnings distance, Do Not Trade) cap the displayed score/label at "Fails" on any FAIL — the UI never shows positive language for an untradeable setup. An UNKNOWN result is labeled "Verify," never a positive score.
- **`classifyReadiness` (`scanner.ts`) is the single authoritative PASS/NEAR/NEEDS_DATA/FAIL readiness answer** — every surface that labels, counts, filters, or promotes a Scanner result (row badges, one-click filters, header counts, the live-scan "near matches" toast, Dashboard's Top Setups selection) must read this, not re-derive its own "near"/"pass" notion. NEAR requires fully complete evidence (including a real option-chain assessment) plus exactly one non-gating near miss; a known failure (gating or not) is always FAIL even when other evidence is also missing. **PASS/NEAR also require actual selected-contract evidence** (`contractReasonCode` absent/null), independent of which scoring rules happen to be enabled — `optionEnrichment === "ENRICHED"` alone only means a chain request was spent, which also covers CHAIN_UNAVAILABLE/NO_PUT_CONTRACTS/no-suitable-strike; those correctly read NEEDS_DATA even with only a stock-level rule (e.g. price) enabled (Astra-found gap, fixed). `isActionableReadiness` (PASS/NEAR only) gates which candidates may enter an actionable list (e.g. Dashboard Top Setups) — a never-option-assessed, no-contract-selected, or otherwise incomplete row must never be promoted there regardless of any historical score it carries.
- **LST Core** (`SCANNER_RULE_DEFINITIONS`) is the canonical default rule set; each user can edit their own `ScannerProfile`/`ScannerRule` and reset to LST Core at any time — editing one user's settings never affects the other's.
- **Saving/resetting Scanner settings never runs a scan** (`updateScannerSettingsForUser`/`resetScannerSettingsToLstCoreForUser`, `workflows.ts`) — a settings change is validated in full before anything is written, then persisted atomically in one `$transaction` (every rule upsert plus a touch of `ScannerProfile.updatedAt`); it never invokes the demo or live scanner and never replaces the latest `ScanRun`. Demo mode is only ever entered by the explicit "Refresh Demo Scan" action (`rerunDemoScannerForUser`). **The settings revision a scan actually evaluated against is captured at scan-read time** (`withSettingsRevision`, `workflows.ts` — stamps `settingsRevisionAsOf` into each persisted result's `snapshotJson`, no schema change), not inferred from `ScanRun.createdAt` (a persist-time value that can land after a settings save that happened mid-scan, which would otherwise hide a real earlier-settings case — Astra-found race, fixed). The Scanner page discloses when the visible results predate the current settings (`resultsPredateCurrentSettings`, comparing `ScannerProfile.updatedAt` to that captured revision, falling back to `run.createdAt` only for a run with no results or one predating this field) rather than presenting stale-rule results as current.
- Live scanning uses a bounded starter universe + the user's own Research tickers, option-chain calls capped, bounded concurrency — see Bounded Provider Usage above. Demo data is always visibly labeled as demo, never presented as live.
- **Every option-derived field on a scanned candidate traces to exactly one selected `OptionContractSnapshot`** (`candidateValues`, `live-scan.ts`) — expiration/strike/bid/ask/delta/liquidity/ROR can never mix evidence from a different strike or expiration by construction. Two ambiguities are made explicit rather than left implicit: (1) `premium` is a mark/midpoint estimate (`premiumBasis: "MARK_MIDPOINT"`), never the amount `ror`/`annualizedRor` are calculated from (`rorBasis: "BID"`, backed by the actual `bidProceedsPerContract` dollar figure); (2) no option-chain provider here has ever supplied a verified per-quote pricing timestamp, so `optionQuotedAt` stays explicitly null while `retrievedAt`/`retrievedOnNonTradingDay` (a coarse NYSE-trading-day check, not exact session hours) disclose only what is genuinely known — a request made on a closed-market day is never presented as a live quote. `earningsWithinHoldingPeriod` compares the selected contract's own DTE against earnings distance so a candidate isn't silently exposed to an earnings event mid-holding-period, without inventing an earnings date when one isn't available.
- **Scanner and Research are separate concepts** (see Product Model) — a Research/personal-exclusion status must never alter a Scan result's technical score, status, or label.
- A separate **Covered Call scanner mode** exists (decision support only, universe = the user's own `ASSIGNED` campaigns) — architecturally distinct from the CSP live scanner, not a generalization of it.
- Full rule catalog and selection algorithm detail: `docs/SCANNER_RULES.md`.

## Financial / Accounting Invariants

- Account/trading performance is derived from the append-only `AccountLedgerEntry` ledger plus confirmed `BrokerRecord` facts — **never** a raw `currentBalance − startingBalance` shortcut, which would silently mix deposits/withdrawals with trading P/L.
- **One authoritative "effective baseline" selection, never a competing interpretation.** `selectEffectiveBaseline` (`accountLedger.ts`) is the single function that decides which `STARTING_VALUE` entry is "the baseline" when more than one exists (a correction) — selection is by `(createdAt desc, id desc)`, **never** `occurredAt` (a correction may deliberately move its own effective date earlier or later than the revision it replaces). `summarizeAccountLedger` and `summarizeAccountPerformance` both read this one result (`ledger.effectiveBaseline`) rather than each re-deriving their own notion of "starting value."
- **A baseline correction is append-only** — `setAccountBaselineForUser` (`workflows.ts`) never updates or deletes a prior `STARTING_VALUE` row; a correction inserts a new one, and the replaced revision's id plus a **required** reason (Astra corrective patch) are recorded in the existing `notes` field (no schema change) — the very first baseline for an account has no prior revision to explain replacing, so its reason stays optional. The prior revision stays in history for audit. Concurrency: the caller supplies the `expectedRevisionId` it last saw as effective; the current effective revision is re-selected inside the same `prisma.$transaction`, now running at **Serializable isolation** (Astra corrective patch — a plain read-committed transaction let two concurrent corrections both pass the same stale-revision check), immediately before the write; a mismatch (another correction landed first) is rejected as a validation error, and a genuine Postgres write-conflict at commit time (SQLSTATE 40001 / Prisma code `P2034`) is caught and translated into the same user-safe "reload and try again" message rather than a raw transaction failure.
- **A baseline date means "whole account value at the end of the selected America/New_York calendar date"** — `endOfNyCalendarDateUtc` (`accountLedger.ts`) converts that NY calendar date to the exact UTC instant for `23:59:59.999` America/New_York, via a guess-and-correct offset lookup (`Intl.DateTimeFormat` reverse lookup at a whole-second guess, then the trailing 999ms is added back). Validates the calendar components themselves before conversion (Astra corrective patch — `Date.UTC` used to silently normalize an impossible date like `2026-02-30` into March) and rejects a still-future baseline instant (a baseline can only record a value that has already happened; the reference "now" is overridable only for deterministic tests). Safe for all real dates including DST transition days since US DST transitions happen at 2am local, far from midnight.
- **Measurement interval, enforced consistently everywhere** (Astra corrective patch — valuation and funding used to disagree): `(baseline.occurredAt, endingAt]`, where `endingAt` is the account's own latest `BROKER_SNAPSHOT` time **only when that snapshot is dated at/after the baseline** (a snapshot from before the baseline describes a different, earlier state of the account and can never serve as the interval's ending valuation — it no longer feeds `currentValue`/`totalGain` at all), else a caller-supplied `asOf`, else "now." Every reconstructed figure respects this same interval now, not just the historically-checked ones: funding at/before the baseline is excluded from contributions (already inside the starting value); funding after `endingAt` is excluded from both contributions AND the ending valuation itself (previously a post-`endingAt` ledger deposit could still leak into `currentValue` through the ledger's own unbounded contribution total even though it was correctly excluded from this function's own contribution sum — a real, fixed bug); dated broker-transaction trading P/L before the baseline is excluded from `tradingPL` rather than double-counted.
- **No date/amount matching is ever used to suppress a broker transfer once an explicit baseline exists** (Astra corrective patch, second pass) — the baseline represents the account's value at its exact opening timestamp; only that timestamp boundary decides whether a transfer is "already inside the baseline" or "a contribution." An earlier version of this fix restricted the legacy same-day/same-amount dedup to only the currently-effective baseline revision (fixing a superseded-revision case), but the dedup itself remained unsafe: a baseline's `occurredAt` is an America/New_York end-of-day instant that lands on the *next* UTC calendar date, so a genuinely new, coincidentally same-amount deposit the following NY afternoon could share that UTC date and get wrongly suppressed. The dedup mechanism has been removed entirely — a transfer strictly after the baseline's exact timestamp is always a contribution, regardless of its amount or calendar date.
- **Funding authority by account type**: a `SCHWAB` account's own imported broker-transfer activity is the funding record of truth — `addAccountLedgerEntryForUser` blocks a new manual DEPOSIT/WITHDRAWAL server-side based on the account's persisted `source`, never live Schwab connection status (stays blocked even while temporarily disconnected). A `MANUAL` account's manual entries remain its funding authority.
- **Whole-account gain requires affirmative evidence on every axis, not just the absence of a detected problem** (Astra corrective patch tightens all of these): `FundingCoverageStatus` is `"COMPLETE" | "INCOMPLETE_INFERRED_BASELINE" | "INCOMPLETE_MIXED_SOURCES" | "INCOMPLETE_UNVERIFIED_SCHWAB_HISTORY"`, and `totalGain`/`totalReturnPercent` are populated ONLY when it is `COMPLETE` **and** a trustworthy, *supported* ending valuation exists (see below). An **inferred** (never explicit) baseline can no longer produce a confirmed gain at all, even with zero detected contributions. A manual ledger contribution and a broker-transfer contribution both landing in the same interval remains `INCOMPLETE_MIXED_SOURCES` — dollar gain is withheld, never guessed, and no historical entry is ever deleted to resolve the ambiguity. A **Schwab-evidenced** account is `INCOMPLETE_UNVERIFIED_SCHWAB_HISTORY` unless BOTH (a) the measurement interval fits inside the trailing window a Schwab sync actually re-fetches (`SCHWAB_TRANSACTION_LOOKBACK_DAYS`, 90 days, `workflows.ts`) — necessary but not sufficient on its own (Astra corrective patch, second pass: "we asked for 90 days" is not proof we received and persisted them) — AND (b) the caller supplies `BrokerTransactionCoverageStatus: "COMPLETE"` (`accountLedger.ts`), its own affirmative proof that this account's transaction fetch AND persistence both fully succeeded. **No caller in this codebase can honestly supply that proof today** — see the architecture-gap note below; every Schwab-evidenced account's funding coverage is therefore `INCOMPLETE_UNVERIFIED_SCHWAB_HISTORY` in production until a future ticket adds real per-account evidence tracking.
- **A whole-account ending valuation can only ever come from a real, supported account-value reading — a valid Schwab `BROKER_SNAPSHOT` dated at/after the baseline. There is no other path, with or without trading evidence** (Astra corrective patch, third pass tightens this to its final form). Trading cash flows (option premium, dated broker-transaction P/L, undated lifetime CAMPAIGNS P/L, or anything derived from them) are never a substitute, no matter how well-dated: receiving option premium also creates an offsetting short-option liability, so "cash received" is not the same fact as "whole-account value changed by that amount" (second-pass repro: a $10,000 baseline plus a $75 Sell to Open premium, no snapshot, used to produce `currentValue: $10,075` / `totalGain: $75`). A second-pass version of this fix still allowed `startingCapital + contributions` to stand in as the ending valuation whenever `tradingPL === null`, reasoning that "no trading" meant contributions were the only possible value driver — that was itself unsafe: `tradingPL === null` proves only that no dated broker option records or campaign fallback were found, never that interest, fees, dividends (`otherIncome` — computed separately from `tradingPL`), or unrecorded changes to pre-existing holdings didn't occur (third-pass repro: a $10,000 baseline with $25 of recorded interest and no ending snapshot used to produce `currentValue: $10,000` / `gain: $0` / `return: 0%` / `status: OK`, silently discarding the $25). This fallback has been removed entirely — a baseline plus ledger funding events alone is never an ending valuation, regardless of trading evidence.
- **Known architecture gap (Astra corrective patch, second pass, Issue 2) — no per-account, per-sync Schwab funding-evidence is persisted anywhere.** `syncSchwabAccountForUser` (`workflows.ts`) computes real per-account evidence (`SchwabAccountSyncResult.accounts[].evidence` — did the transaction fetch and its persistence both succeed for this account, this sync) but it lives only in memory for that one request, consumed by campaign reconciliation and then discarded. The one thing that *is* persisted, `BrokerConnection.metadata.lastSyncDiagnostics` (`broker-connections.ts`), is a **connection-level aggregate across every Schwab account the user has linked** — not scoped to one account or to a measurement interval, so it cannot honestly serve as per-account proof (a user with two linked Schwab accounts could have one succeed and one fail, and the aggregate would not say which). `AccountPerformanceInput.brokerTransactionCoverageStatus` (`accountLedger.ts`) exists so the domain logic is ready the moment real evidence exists — proven directly in `accountLedger.test.ts` — but wiring up genuine per-account, per-interval evidence would need a new persisted, account-scoped field (a schema change), deliberately not done in this patch.
- **Account gain rule**: whole-account dollar gain = ending value − beginning value − deposits + withdrawals, exposed only under the affirmative-evidence rule above. This is never a cash-flow-weighted percentage return — `totalReturnStatus` stays `CONTRIBUTIONS_NEED_ADVANCED_RETURN` whenever contributions exist in an otherwise-complete period; a proper TWR/XIRR engine is future work (Roadmap item 10).
- **The two prior 1%-target displays, plus a third missed on the first pass, are retired**, not replaced: the Tracker's `GoalTracker` component, its "1% Goal Pace" metric card, its "Performance vs 1% Target" chart (`PerformanceGoalChart` — an Astra corrective-patch follow-up; missed in the first retirement pass), and the Dashboard's weekly-percent-of-target block were all removed in favor of neutral "Trade-return goal reporting is being rebuilt from verified account and trade data." copy (Dashboard keeps its W-L record display, which was never part of the misleading metric). The underlying `summarizeContributionAdjustedGoal`/`summarizeWeeklyReturns` domain functions were deliberately left in place, unused by any page today, pending the next performance ticket.
- Only `CLOSED` campaigns count toward win/loss; an `OPEN` campaign's net cash flow (even if positive) is never counted as a completed win.
- **Confirmed vs. incomplete/provisional data must stay visibly distinct**: `src/domain/finance/performance.ts` exports a shared `CompletenessStatus` (`CONFIRMED | PENDING | INCOMPLETE | NOT_APPLICABLE`) - `WinLossSummary`/`ThisWeekSummary` compute `wins`/`losses`/`winRate` from CONFIRMED outcomes only (`confirmedCount`/`pendingCount` expose the split), and `CampaignProgressSummary` carries `currentPLStatus`/`projectedOtmStatus` per campaign. An unresolved Schwab fee shows "Pending"/gross-only, never a fabricated confirmed net number (`feesFullyKnown`/`netPLExact`/`grossPL`) and is excluded from the confirmed win/loss denominator. A missing cost-to-close/current-price source means the current mark is shown as unavailable (PENDING), never guessed; a legacy event missing required fields is INCOMPLETE, distinct from a campaign where the metric genuinely doesn't apply (NOT_APPLICABLE) - see `getOpenPutEvidenceState` (`campaigns.ts`). An `ASSIGNED` campaign's current valuation is INCOMPLETE, not NOT_APPLICABLE, since real exposure exists with no valuation engine yet (Roadmap item 7). `currentCollateralCommitted` (the *currently* open leg's own collateral) is distinct from `collateralCommitted` (a lifetime high-water mark used only for closed-campaign return-on-collateral) — using the wrong one for "what's secured right now" was a real, fixed bug (see Roadmap status).
- Deposits/withdrawals are never presented as trading profit or loss. Total gain, trading P/L, other income, current/mark-to-market P/L, and projected-OTM P/L are separate, explicitly labeled figures, not blended.
- Full methodology: `docs/ARCHITECTURE.md`, `docs/LST_DOMAIN.md`, and the archive's Account Ledger / Performance Methodology section.

## Reporting Domain (Reporting Phase, Ticket 1)

- **`src/domain/finance/reporting.ts` (`summarizeAccountReporting`) is the one authoritative reporting-domain summary future Dashboard/Tracker/Account UI must consume** — it exists specifically so financial formulas and evidence-status interpretation live in exactly one place instead of being reinvented per page. It is a thin, non-reimplementing wrapper: every number it exposes is a passthrough or a simple, documented combination of `accountLedger.ts` (whole-account value/gain/return, `summarizeAccountPerformance`/`summarizeAccountsPerformance`), `performance.ts` (`summarizeWinLoss`, `summarizeThisWeek`), and `brokerPositions.ts` (`summarizeCampaignExposure`) — it never fetches data and never scopes by owner itself, trusting the caller to have already scoped `accounts`/`completedCampaigns`/`openExposure` to one viewer's own data.
- **Four concepts stay explicitly separate, never blended into one percentage**: Account Value (what the account is worth right now — may be available even when gain isn't), Confirmed Trading P/L + Trade Return (how the trades themselves performed on capital actually committed, excluding idle cash), Current Capital Utilization (how much of the account is committed right now — point-in-time only, no average/historical utilization), and Whole-Account Gain/Return (gated entirely by the already-approved baseline/funding evidence rules from Ticket 9 — no new accounting math).
- **Confirmed Trading P/L resolved an existing naming ambiguity**: `summarizeWinLoss.confirmedRealizedTradingPL` (CLOSED campaigns, CONFIRMED-only, fee-inclusive) is the one true "confirmed trading P/L" — deliberately NOT `accountLedger.ts`'s `tradingPL` (a broader cash-flow figure that includes STILL-OPEN positions' option premium — a different, useful-but-different concept for "Trading Cash Flow"), and NOT `summarizeWinLoss.realizedTradingPL` (which blends in PENDING campaigns). It is exposed as an `ALL_TIME` figure since `summarizeWinLoss` has no artificial window, unlike Trade Return.
- **Trade Return exposes only `THIS_WEEK`** (`summarizeThisWeek`'s return on secured capital) — the one period this ticket's math is already proven safe for. Generalizing to 4-week/all-time trade return, average/historical capital utilization, a capital-time-exposure engine across concurrent campaigns, and a new capital-time-weighted 1% weekly trade-return goal are all explicitly deferred (see the read-only design-pass report from this same phase) — Trade Return and period-average utilization would share that same new aggregator when it's eventually built.
- **Current Capital Utilization** = (`securedPutCollateral` + `assignedShareCapital`, both from `summarizeCampaignExposure`) ÷ `currentAccountValue`. Including `assignedShareCapital` (assigned-but-unsold shares' cost basis) was a deliberate judgment call: assigned shares are real capital at work, not idle cash, and `summarizeCampaignExposure` already keeps the two components cleanly separate (an assigned campaign's stock position is never misrepresented as an active CSP) — both are exposed as their own sub-fields (`currentCapitalCommittedSecuredPut`/`currentCapitalCommittedAssignedShares`) for transparency. Unavailable (never guessed) whenever there is no valid current account value to divide by.
- **Friendly availability reasons are centralized** in `friendlyReportingReason` (`reporting.ts`) — the only function that should ever translate an internal status/reason code into user-facing copy; no page should independently invent or reinterpret this wording. Raw enum names (e.g. `INCOMPLETE_UNVERIFIED_SCHWAB_HISTORY`) must never reach the UI directly.
- **No UI changes were made in this ticket** — Dashboard/Tracker/Account still compute their own figures directly from `accountLedger.ts`/`performance.ts`/`brokerPositions.ts` today (including several pre-existing duplicate renderings of whole-account gain/return across pages, flagged in the design-pass report as needing consolidation). Wiring pages to consume `summarizeAccountReporting` instead, and deleting their now-redundant local formulas, is Reporting Phase Ticket 2+.

Fixed by removing the date/amount dedup entirely - only the measurement interval's exact timestamp boundary now decides whether a transfer is a contribution, matching the ticket's explicit rule that a baseline's own timestamp is the sole authority. **Issue 2:** funding coverage could reach `COMPLETE` for a Schwab-evidenced account purely because the measurement interval fit inside the 90-day lookback window - but `syncSchwabAccountForUser` writes the account/balance `BROKER_SNAPSHOT` unconditionally and then fetches/persists transactions as later, independently-failable steps, so a short interval never actually proved the transaction fetch or its persistence succeeded (exact repro: a $10,000 baseline, a Schwab snapshot showing $12,000, and a silently-failed transaction fetch behind it - previously reported `COMPLETE`/`gain: $2,000` with zero funding evidence). Investigated the Schwab sync/import persistence model first, as directed, and found **no existing persisted evidence** capable of proving per-account, per-interval transaction coverage - see the "Known architecture gap" note above. Fixed by adding `BrokerTransactionCoverageStatus`/`AccountPerformanceInput.brokerTransactionCoverageStatus`, an explicit caller-supplied proof that defaults to absent; fitting inside the lookback window remains necessary but is no longer sufficient. **Issue 3:** a whole-account ending valuation could be reconstructed from option-premium/trading cash flows even when no real account-value reading existed at all (exact repro: a $10,000 baseline plus a $75 Sell to Open premium, no broker snapshot, previously produced `currentValue: $10,075`/`gain: $75`) - wrong because receiving option premium also creates an offsetting short-option liability, so cash received is not the same fact as whole-account value changed. Fixed by restricting the MANUAL-reconstruction fallback to only fire when NO trading activity occurred in the interval at all (`tradingPL === null`) - a valid Schwab `BROKER_SNAPSHOT` dated at/after the baseline is now the only way to establish a supported ending valuation whenever any trading occurred. 1103/1103 non-DB tests (25 new across two new describe blocks in `accountLedger.test.ts` covering all three issues' required regressions, including the exact Astra reproductions; 4 more inline in the existing Issue-1 describe block), plus updates to 9 pre-existing `accountLedger.test.ts` assertions that had encoded the now-fixed bugs (including rewriting one original-ticket test's fixture to use a realistic end-of-day baseline timestamp instead of an artificial midnight-UTC one, and replacing one test that exercised the now-removed dedup outright), TypeScript, ESLint, production build, and `git diff --check` passed. DB integration tests and live-provider/browser verification were not performed - local Docker/Postgres remain unavailable in this environment (same limitation as every prior ticket); the funding-coverage-evidence mechanism in particular could only be verified structurally (via directly-constructed domain-level test fixtures), since no real Schwab sync producing genuine per-account evidence could be exercised. No schema migration. The non-blocking item Astra also noted (campaign-level "Goal Need" still contains a 1%-based comparison, `summarizeContributionAdjustedGoal` remains called) was investigated and found NOT trivially removable - the account-level `ownGoal` it produces still feeds the legitimate, unrelated "Projected OTM P/L" metric card, and "Goal Need" itself is computed entirely from per-campaign `summarizeCampaignProgress` output, not from `ownGoal` - recorded below as a genuine non-blocking follow-up rather than acted on, per the ticket's explicit instruction not to expand into campaign-level decision-aid redesign.

**Third Astra corrective patch on Ticket 9 (base `1929b09`, local only):** Astra found one remaining unsupported whole-account valuation path, fixed narrowly within `accountLedger.ts` alone, no schema migration.
